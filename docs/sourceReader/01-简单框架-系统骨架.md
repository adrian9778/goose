# 01 · 简单框架：系统骨架

> 层级：L1 简单框架 · 本文只答「系统由什么组成、请求怎么走」，不展开状态机/Provider/扩展的实现细节（见 03/04/07）。

## 一句话定位

goose 是一个用 Rust 实现的 **AI Agent 框架**，对外暴露三种形态：

- **CLI**（`goose-cli` crate）：交互式/无头会话，直接跑状态机；
- **ACP server**（`goose` crate + `goose-cli` 的 `acp`/`serve` 子命令）：按 Agent Client Protocol 对外提供 agent 能力；
- **桌面应用**（`ui/desktop`，Electron）：主进程通过 `goose-acp` npm 包拉起 ACP 子进程，渲染进程通过 ACP over WebSocket 连接。

所有形态共享**同一个核心 agent 循环**：`crates/goose/src/agents/` 里的 `StateMachineServices` + `state_machine/*`。

## Cargo workspace 组成

`Cargo.toml` workspace 成员 = `crates/*`（15 个 crate）。核心分层如下：

| crate | 定位 | 关键内容 |
|---|---|---|
| `goose` | 核心库（agent 逻辑 + ACP server） | `agents/`（状态机、扩展管理、provider 管理）、`acp/`（ACP 协议服务）、`config/`、`session/`、`recipe/`、`providers/`（ProviderDef 定义层） |
| `goose-cli` | CLI 入口 | `main.rs`（tokio runtime 启动）、`cli.rs`（clap 命令）、`session/`（CliSession 交互/无头循环） |
| `goose-agent` | GDK 的 Agent Loop | `machine.rs`（`StateMachine` 泛型）、`operation.rs`（`Operation` trait）、`events.rs`（`AgentEvent`）、`subagent.rs` |
| `goose-providers` | Provider 具体实现 | Anthropic/OpenAI/Azure/Databricks/Bedrock 等，OpenAI 兼容层 |
| `goose-provider-types` | 共享类型 | `conversation`（消息/会话）、`permission`、`thinking`、`retry`、`formats` |
| `goose-mcp` | 内置 MCP server | `memory`、`tutorial`、`autovisualiser`、`computercontroller`、`peekaboo` |
| `goose-sdk` | GDK Rust SDK | 给第三方的 agent SDK，uniffi 绑定 |
| `goose-sdk-types` | GDK 共享类型 | `custom_notifications`、`custom_requests` |
| `goose-context-management` | 会话压缩 | `summarize`、`templates`、`structured` |
| `goose-roaming` | P2P 漫游传输 | iroh 基底的 P2P agent 漫游 |
| `goose-local-inference` | 本地推理 | llama-cpp / mlx / HuggingFace 后端 |
| `goose-acp-macros` / `goose-download-manager` / `goose-test` / `goose-test-support` | 辅助/测试 | 宏、下载、测试工具 |

> 注：`goose-sdk` 与 `goose-agent` 是 **GDK**（goose Development Kit）的公开 crate（`release-plz.toml` 里 `release = true`）；`goose` 与 `goose-cli` 的 `pub` 项是内部实现，无稳定 API 承诺。见 `AGENTS.md`。

## 进程模型

```text
┌─────────────────────────────────────────────────────────────┐
│  CLI 进程（goose-cli 二进制）                                 │
│   main.rs:tokio runtime ──▶ cli() ──▶ 命令分发               │
│     ├─ Command::Session ──▶ CliSession.interactive()         │
│     ├─ Command::Run     ──▶ CliSession.headless()            │
│     ├─ Command::Acp     ──▶ acp::server::run()（stdio）       │
│     ├─ Command::Serve   ──▶ ACP over HTTP+WebSocket           │
│     ├─ Command::Mcp     ──▶ goose-mcp 内置 server（stdio）    │
│     └─ ...                                                  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  Desktop（Electron）                                          │
│  主进程 ──spawn──▶ goose-acp 子进程（ACP over stdio）        │
│  渲染进程 ──WebSocket/Streamable HTTP──▶ ACP endpoint        │
│  ui/desktop/src/acp/acpConnection.ts:openConnection          │
└─────────────────────────────────────────────────────────────┘
```

每个形态都汇聚到 `StateMachineServices::reply`（`crates/goose/src/agents/services.rs:813`），后者构建状态机并 `run_goose`。

## 主数据流（CLI 交互会话）

一次 `goose session` 的完整数据流：

```text
main() ─▶ cli() ─▶ Command::Session ─▶ handle_interactive_session
  ─▶ build_session()（builder.rs:647）── 构建 StateMachineServices::with_config(cli())
  ─▶ CliSession::new()
  ─▶ CliSession::interactive(prompt)   # 读入用户输入
  ─▶ CliSession::process_agent_response ─▶ services.reply(user_message, session_config)
  ─▶ reply()  ─▶ start_reply()  ─▶ turn()
  ─▶ run_machine()  ─▶ create_state_machine() ─▶ build_state_machine()
  ─▶ run_goose(&machine, session_manager, hooks, session_id, emit)
  ─▶ StateMachine::run()  # 循环 step→apply，直到 RunStatus::Yielded/Cancelled
  ─▶ 事件流（AgentEvent）回 CLI，渲染 markdown / 工具确认 / elicitation
```

## 状态机操作集（`build_state_machine`，骨架级）

`build_state_machine`（`goose/src/agents/state_machine_builder.rs:89`）把以下 operation 串成 steps（每步是 `Step::Operation` 或末尾 `Step::Inference`）：

```text
SlashCommandOperation ─▶ [ToolApprovalOperation, SkillOperation, RecipeOperation,
  ToolExecutionOperation, RemainingToolCallsOperation, SubagentOperation,
  SteerOperation, BangShellOperation]
  +（若不管理自己的 context）[ContextRelevanceOperation, CompactionOperation]
  + [ToolPairCompactionOperation, DoctorOperation, ProjectOperation, RetryOperation,
     EmptyResponseOperation, StopHookOperation, ExitOnErrorOperation, MaxTurnsOperation]
  + extra_operations（auto_effort）
  + StatusOperation（并入 command_handlers）
  ─▶ Step::Inference(InferenceRunner)
```

每个 operation 依次在每轮 `step()` 里被调，命中条件才返回非 `not_applicable`，产生的 `GooseEffect` 由 `run_goose` 经 `apply_effects` 落盘（`state_machine/session.rs`）。

## ACP 协议边界（骨架级）

ACP server 由 `goose/src/acp/` 提供：

- `server.rs`：`AcpConnection`（单连接会话持有 `StateMachineServices`）、`serve()`（stdio 的 `SacpAgent` 桥）、`run()`（`Command::Acp` 入口，`server.rs:2619`）；
- `server_factory.rs`：`AcpServer` 负责懒建共享 `services`，支持 `enable_scheduler`（schedule.json）与测试钩子；
- `provider.rs`：`AcpProvider`（把 ACP agent 当作 provider，供 `amp-acp`/`claude-acp` 等客户端复用）。
- `Command::Serve` 走 HTTP+WebSocket（feature `acp-http`），经 `LazyAcpConnection` 按连接建 `AcpConnection`（`server.rs:2603`）。

## 输入/输出

- **输入**：用户消息文本（CLI）、ACP `prompt` 请求、recipe 调度触发、subagent 委托。
- **输出**：`BoxStream<Result<AgentEvent>>` —— 消息增量、工具调用/结果、usage、MCP 通知。CLI 渲染为终端；ACP 序列化为协议 JSON；Desktop 经 WebSocket 推给 UI。

## 配置入口（骨架级）

- `Config::global()`（`goose/src/config/base.rs`）读 `config.yaml` + 环境变量 + keyring secrets。
- 会话/扩展/model 覆盖经 CLI flag（`SessionBuilderConfig`，`builder.rs:158`）与 `resolve_provider_and_model`。
- 每轮 `TurnSettings::from_config`（`services.rs:130`）从配置取重试/压缩/停止钩子阈值。

> 更细节的配置与数据流见 `06-配置与数据流.md`；状态机与并发见 `07-状态机与并发.md`。
